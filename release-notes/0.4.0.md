A minor release: the kernel now carries the statistics a browser needs for a PK summary table, the summary of a parameter table, the time to steady state and the normal and Student t quantiles, so a host can run them without scipy.

## New python entry points

- `summarize(request)`: the summary statistics of raw parameter values, `ParameterResult.summarize` of the host. It returns `mean`, `sd`, `se`, `cv`, `ci_low`, `ci_high`, `median`, `q25`, `q75`, `min`, `max`, `count`, `geomean` and `geocv` per variable and group.
- `time_to_steady_state(request)`: the time to steady state of the troughs of the dosing intervals, `time_to_steady_state` of the host, by the monoexponential approach to the plateau or the stepwise trend test of PKNCA. It returns `tss` per row and, for the monoexponential estimate, the plateau `c_ss`.
- `normal_isf(p)`: the normal quantile of the upper tail.
- `student_t_isf(p, df)`: the Student t quantile of the upper tail.
- `student_t_sf(t, df)`: the Student t survival function `P(T > t)`.

A malformed request to `summarize` or `time_to_steady_state` is a plain `ValueError` and never an `UnsupportedError`, so a host does not mistake a wrong request for a refusal and answer it with its own path.

## The quantiles are the kernel's own

The normal and Student t quantiles, the percentiles of the summary (the bit-exact `numpy.nanpercentile` rule) and the t interval are now computed by the kernel and no longer by scipy. A summary confidence interval can therefore differ from release 0.3.0 in the last bits. The median is percentile 50 of that same rule, which interpolates the two middle order statistics as `a + 0.5 * (b - a)` where `numpy.nanmedian` averages them as `0.5 * (a + b)`: the two differ in the last bits on about 15 % of the groups of an even finite count, so a host which took the median from `nanmedian` sees the same kind of change (`pkpdutils` now takes it from its own percentile helper, for the two engines to agree bit for bit). A table compared across the two releases should be compared with a tolerance, not bit for bit.

## A public API addition of the core crate

`pkpdutils-core` now exports `normal_isf`, `student_t_isf` and `student_t_sf` through `pub use stats::{...}` in `crates/core/src/lib.rs`. This is an intentional addition to the public API and a Rust consumer may rely on it. The rest of the `stats` module stays private.

## A behaviour change: the unbounded optimum of the monoexponential time to steady state

The monoexponential time to steady state now returns `NaN` when the optimum of the fit is unbounded. Before, a flat, falling or never plateauing series of troughs produced a finite but meaningless number. The python library had the same defect and was fixed together with the kernel. The number it used to return changed by orders of magnitude with the starting values of the optimizer, so it was never reproducible.

One narrower case returns `NaN` as well, where a noise free series previously got a stable answer, and it is again a series with no observable approach to a plateau: troughs so nearly straight that `k * t_last` falls below about 0.005, where `k` is the rate of the approach and `t_last` the time of the last trough. At the default fraction of 0.9 that is a time to steady state of about 460 times `t_last`. Both engines switch there, between a `k * t_last` of 0.006 and 0.005 and whatever the number of troughs, because 0.005 is the lowest rate the search looks at: the first start is `0.5 / t_last` and the bracket around it is two decades wide.

At the other end a series can be so fast that its troughs are at the plateau to the resolution of a double, and there the two engines differ. Measured on uniform grids of 4 to 30 intervals, with the first trough a relative distance `g` below the plateau: both still answer at a `g` of `1e-10`, the kernel to six digits and python to within a percent; from a `g` of about `1e-11` the python search stops short of the optimum, where its cost ties the cost at the edge of the range, and reports `NaN`; the kernel brackets the optimum instead and keeps returning the rate through `1e-11` and `1e-12`, and with four troughs down to `1e-16`. It gives up once the rise itself is numerical noise, at a `g` of about `1e-12` for 8 to 30 troughs. Such a series is a half-life a fortieth of the dosing interval or less, and the quantity is of no consequence to a study at that point, but a host which runs both engines has to allow for the difference. Giving python the kernel's bracketed search would settle it and is not part of this release.

## Compatibility

No change to `batch/1`, `analysis/1` or the options, and `analyze_batch` and `is_supported` behave as in 0.3.0. `pkpdutils` can move its floor to this release to route the summary, the time to steady state and the quantiles to the kernel.
