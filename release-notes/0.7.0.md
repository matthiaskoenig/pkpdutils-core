A minor release: the kernel runs in a browser. `pkpdutils-wasm` is a WebAssembly module of the same code the python wheel carries, and `pkpdutils-core` on npm is the JavaScript host which drives it: a request in, the columns of a result out, no python and no server.

## The module

One `cdylib` for `wasm32-unknown-unknown` with the raw C ABI of the engine of `sbmlsim-core`, so a page which drives both learns one layout: no wasm-bindgen, no WASI shim and **no import of any kind**, which means a page instantiates it with an empty import object. `crates/wasm/tests/imports.rs` walks the sections of the built module and asserts it.

The entry points are `pkpd_analyze` (a batch and its options), `pkpd_summarize` (the statistics of a parameter table over its samples) and `pkpd_about` (the version of the build, the version of the output layout, the contracts it speaks and the entry points it carries, which a loader reads rather than probing for a symbol). A page allocates bytes with `pkpd_alloc`, writes a JSON request into them, calls an entry point, reads the answer at `pkpd_output_ptr` for `pkpd_output_len` bytes and frees its request.

An output is a `u32` header length, a JSON header, zero padding to a multiple of eight and then the `f64` values, little endian and row major, so a page reads the payload in place with a `Float64Array`. The header is the result without its numbers: the contract, the sample dimensions and their shape, the row count, every column with its unit, its width and its fill, the text variables with their values, the coordinates and the attributes. The payload is every numeric column in the order the header declares: the parameters, the flag word of every sample, the boolean variables and then the point variables.

Nothing traps. A request which is no UTF-8 or no JSON, a contract skew, an analysis this build does not carry, a bug of the build and a panic are error headers of the four kinds `malformed`, `refused`, `internal` and `panic`, and every entry point returns 0 for an answer and 1 for an error. A panic is a sentence and not a bare `RuntimeError`: the hook writes it into the output buffer before the trap and the loader reads it afterwards. An answer past 2 GiB is refused by the arithmetic rather than attempted, and an allocation which fails below that ceiling is the other sentence: a batch to analyse in shards and a page out of memory are two different things to do something about.

## The npm package

`pkpdutils-core` on npm is the same version as this release. `createRuntime({module})` is one call, `createPool({module})` runs one instance per worker and cuts the rows of a batch into one shard per worker, and the whole package has no dependency: the loader uses no Node API, so the one file runs in a browser, in a Web Worker and in Node.

`column(name)` of a pool is the column of one instance, value for value, which took a new public lookup to be true of every column: `pkpdutils_core::parameter_fill(name)` is the value a row which does not report a parameter contributes to its column - `NaN` for a number which is missing and 0 for a variable carrying an integer code. A batch of an intravenous and an extravascular row reports `cl` for the one and `cl_f` for the other, so two shards report different columns and the merge has to fill them exactly as the kernel fills them. Every column of the wasm header carries that value, so a host merges without keeping a table of its own. What a merge does not reproduce is the order of the columns of a batch of mixed routes, which is the order the shards first report them: a caller reads a column by name, which is what `column(name)` is for.

`js/README.md` is the page a user of the package reads. The first publish of the package is a manual step of the maintainer, because npm trusted publishing is configured per package and a package has to exist before it can be configured; `docs/release.md` says so next to the PyPI half, and every later release goes through the `npm` job of the release workflow.

## The two builds answer the same numbers

`scripts/wasm_fixtures.py` writes eight requests with every column the **native** build answers for them as the hex bits of its `f64` values, and `js/test/same_bits.test.mjs` asks the module for the same numbers. Five of the cases agree bit for bit: a single dose curve, two individual subjects, an infusion, a batch of two routes - the case the per-column fill exists for - and a curve whose dose is 0, the infinities of its dose normalized columns included.

The other three agree to a relative `1e-8`, and the reason is one line of the toolchain: `f64::exp` and `f64::ln` are the libm of the platform natively and the `libm` crate on `wasm32-unknown-unknown`, two implementations of one function which differ in the last bit. The worst disagreement measured is 8.9e-10, in the standard error of the terminal slope of a multiple dose curve, where a cancellation stands over values which differ in their last bit; the delta method is next at 1.2e-12, because its difference quotient divides by a step of a hundredth. Both are the amplification those estimators are built on. A value which is not finite has to match whatever the case: a `NaN`, an infinity and the sign of a zero are of the analysis and not of the target. The same split holds for the macOS and the linux wheel of any release of this package, which call two libms as well; that it is now measured is what this release changes about it.

## The numbers

`bench/RESULTS.md` holds them, measured in Node and in Chrome on the shapes of `docs/benchmark.md` of `pkpdutils`. One curve of twelve points costs 0.19 ms end to end in Node, against 3.16 ms through `nca()` of the python package on the same machine, almost all of which is the python front end: an interactive page is not waiting for this module. On a batch of a hundred thousand curves the pool of eight workers is worth 2x in Node and 3x in Chrome rather than eightfold, and the columns of the table say where the rest went - the JSON of the request is a third to a half of the call, and the shards are cut and cloned on the main thread. A binary request path is the answer to that and is deliberately not in this version; the readable wire is what the fixtures above compare to the bit.

## Also

- `crates/wasm` is a default member, so `cargo test`, `cargo clippy` and `cargo doc` cover it; the whole layer is tested natively, since every entry point is a thin wrapper around a pure function the tests call.
- the `js` job of continuous integration builds the module, lints and tests the crate, runs the tests of the package and packs the tarball. The module is not committed: `node js/build.mjs --check` refuses one older than the crates, so the tests cannot pass against yesterday's kernel.
