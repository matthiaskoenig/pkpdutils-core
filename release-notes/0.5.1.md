# Release notes for pkpdutils-core 0.5.1

A patch release of the extension module and of nothing else: the macOS wheel links no mimalloc. The numerics, the python surface and the wire are those of 0.5.0.

## The fix

The wheels of 0.4.0 to 0.5.0 set mimalloc as the `#[global_allocator]` of the extension on every platform. On macOS that is not a choice a wheel is allowed to make. mimalloc keeps the heap of a thread in the pthread TLS block, and on macOS, where a first access to a `__thread` variable can call `malloc` and recurse into the allocator, it does not use a thread local: it claims two slots by compiled in number, 108 and 109 in the version `mimalloc 0.1` builds today and 89 in the one before it, and reads them with inline assembly off `tpidrro_el0`. The slots are process wide. Two extension modules which each link a copy of mimalloc therefore own the same two: every allocation of the one reads the heap the other left in the slot, takes blocks out of the free lists of pages owned by a heap of the other instance without a lock, because the heap of a thread needs none, and frees blocks through a page map which never saw the arena they came from.

What follows is heap corruption, and its symptom is anything at all, in code which has no bug, serially as much as in parallel: a `usize` larger than `u32::MAX` inside a dependency, an `assert_eq!` of a dependency on a state it cannot reach, a `SIGBUS` while a backtrace is symbolized.

This was observed rather than deduced. `sbmlsim-core` sets the same mimalloc as its own global allocator, and the test suite of `sbmlsim`, which imports both extensions into one interpreter, failed on macOS with exactly those symptoms: 25 failures and 26 errors with both modules loaded, a clean run of the same commit with this module held back, and a clean run on linux x86_64, linux aarch64 and windows with both.

The macOS wheel now allocates through the system allocator. Every other platform keeps mimalloc, because no other platform has the collision: the ELF targets give each shared object its own initial-exec TLS block and windows allocates a slot per instance with `TlsAlloc`. Pinning the other major version of mimalloc would only move the collision to whatever extension pins that one, and a wheel cannot know what else an interpreter will load.

## What a caller sees

- On macOS the allocator is the system one, and what that costs there **has not been measured**. The figure which justifies mimalloc elsewhere is a linux one: about 22 percent of the CPU time of a batch of 100 000 rows by 12 points, the shape where allocation is on the hot path, against glibc malloc, with the dense shapes neither gaining nor losing. It is no bound on the macOS difference in either direction, since the system allocator there is libmalloc and not glibc malloc. The macOS wheel also no longer pays mimalloc's third more peak resident set size on that shape.
- A source install on macOS no longer builds mimalloc's C sources, so it no longer needs a C toolchain for them.
- `pkpdutils_core.__allocator__` is new and reports `"mimalloc"` or `"system"`, so which of the two a build is can be answered by the artifact rather than by a comment. It is the first thing to ask of a wheel which behaves impossibly next to another extension module.

No host change is needed. `pkpdutils` 1.6.0 and later resolve this version through `pkpdutils-core>=0.5.0,<0.6`.
